# Порівняння ролей у проєкті

Порівняння ролей, які найчастіше плутають у гібридному проєкті (Waterfall для планування, Scrum для розробки), і як вони розподілені в CSS. Склад команди й підпорядкування: [OBS](confluence/parts/05-obs.pdf), відповідальність по пакетах робіт: [RACI](confluence/parts/07-raci-matrix.pdf).

## 1. Project Manager, Product Owner, Scrum Master

| | Project Manager | Product Owner | Scrum Master |
|---|---|---|---|
| Головне питання | Чи вкладемося в строки, бюджет і обсяг? | Що будуємо і навіщо, у якому порядку? | Чи працює процес Scrum і що заважає команді? |
| Фокус | Проєкт: план, ризики, бюджет, стейкхолдери | Продукт: цінність, беклог, пріоритети | Команда й процес: події, самоорганізація |
| Рішення | Plan, Change Request, ескалація, ресурси | Склад і порядок Product Backlog, приймання історій, скасування спринту | Як покращити процес; усуває перешкоди |
| Володіє артефактами | Charter, Risk Register, Gantt, Communication Plan | Product Backlog, цілі продукту, Sprint Goal (спільно з командою) | Допомагає з Sprint Backlog, DoD, ретроспективою |
| Звітує | Спонсору (status report) | Стейкхолдерам, команді | Команді й організації |
| Не робить | Не вирішує технічне «як» | Не диктує, як розробники реалізують | Не призначає задачі й не керує людьми |
| Горизонт | Весь проєкт до закриття | Життя продукту | Кожен спринт |

Ключова різниця: PM відповідає за **рамку** (строки, гроші, ризики), PO за **вміст** (що саме робимо), SM за **спосіб роботи**.

## 2. Хто що вирішує між PO, Developers і SM (Scrum Guide 2020)

| Рішення | PO | Developers | SM |
|---|---|---|---|
| Що входить у Product Backlog і в якому порядку | Вирішує | Консультує оцінками | Допомагає з технікою ведення |
| Скільки роботи взяти в спринт | Пропонує ціль | Вирішують | Фасилітує планування |
| Як реалізувати задачу технічно | Не втручається | Вирішують | Не втручається |
| Чи відповідає Increment вимогам | Приймає за критеріями | Гарантують якість за DoD | Стежить, щоб DoD існував і діяв |
| Скасувати спринт | Єдиний може | Ні | Ні |

## 3. Суміжні ролі проєкту

| Роль | Відповідальність | Відмінність від PM |
|---|---|---|
| Project Sponsor | Фінансує, затверджує Charter, консультується щодо go-live | Дає повноваження й гроші, не керує щоденно |
| Business Analyst | Вимоги, UML, доменна експертиза | Відповідає за «що потрібно», PM за «коли й за скільки» |
| Tech Lead | Архітектура, технічні рішення, code review | Відповідає за технічну якість, PM за терміни й ризики |
| UI/UX Designer | Макети інтерфейсу | Відповідає за зручність, не за план |
| Back-end / Front-end Developer | Реалізація модулів | Виконують пакети, оцінюють трудомісткість |
| DevOps Engineer | CI/CD, розгортання, реліз | Відповідає за середовища й доставку |
| QA Engineer | Тестування State Machine й бізнес-логіки | Незалежна оцінка якості, дає дані для приймання |

## 4. Як це влаштовано в CSS

- Окремого Scrum Master у структурі команди (OBS) немає. Фасилітацію подій Scrum бере на себе PM.
- Функції Product Owner поєднано з PM: пріоритет історії підтверджує «Product Owner / PM» (див. [DoR / DoD](confluence/parts/02-dor-dod.pdf)).
- Таке поєднання прийнятне для навчального проєкту, але в реальному проєкті воно створює ризик конфлікту інтересів: PM захищає строки й бюджет, PO відстоює обсяг. Тому в [Communication Plan](confluence/parts/10-communication-plan.pdf) і [Change Log](confluence/parts/11-change-log.pdf) зміни обсягу йдуть через Change Request з окремою оцінкою.
- Ролі користувачів системи (Клієнт, Менеджер, Логіст) не є ролями проєкту: їх описано в [PRD](confluence/parts/15-prd.pdf), [таблиці контрактів](api-contracts.md) і README.
